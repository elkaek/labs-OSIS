## 3. Настройка SSH-доступа и удаленное подключение

Служба безопасной оболочки (`SSH`) была выбрана и инсталлирована ещё на этапе первичной установки системы. Для организации удаленного доступа с основной (хостовой) машины под управлением Windows потребовалось проверить её статус и настроить сетевой проброс.


### Настройка аутентификации по SSH-ключам

Для безопасного подключения к виртуальной машине без вечного ввода пароля была настроенна авторизация по крипто ключам.

#### 1. Генерация пары ключей на хост-машине

В терминале основной системы была создана новая пара ключей:
```bash
ssh-keygen -t ed25519
```
В результате в каталоге пользователя (C:\Users\Thunderobot\.ssh\) сформировались два файла:
* `id_ed25519` приватный ключ, остаётся на основном компьютер
* `id_ed25519.pub` публичный ключ, для передачи на удалённый сервер

<img width="913" height="545" alt="Снимок экрана 2026-11-20 010944" src="https://github.com/user-attachments/assets/cbc0e4f5-fc0f-4c82-990b-fbe70e684206" />

#### 2. Копирование публичного ключа на виртуальную машину

Чтобы сервер распознавал клиент при подключении, содержимое публичного ключа было добавлено в файл авторизованных ключей el:

`~/.ssh/authorized_keys`

Передача ключа с основного компьютера через Windows PowerShell с учётом проброшенного порта 2222

`Get-Content \$env:USERPROFILE\.ssh\id_ed25519.pub | ssh -p 2222 el@127.0.0.1 "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"`

#### 3. Разграничение прав доступа на сервере

Для корректной работы службы OpenSSH внутри виртуальной машины были заданы строгие права доступа

`chmod 700 ~/.ssh`
`chmod 600 ~/.ssh/authorized_keys`
* `700` полный доступ к директории .ssh разрешён только её владельцу
* `600` чтение и запись файла `authorized_keys` доступны только владельцу учётной записи

<img width="1449" height="466" alt="Снимок экрана 2026-11-20 011643" src="https://github.com/user-attachments/assets/08daa27f-8372-4a96-a29c-fb3709ce7593" />

#### 4. Проверка подключения в режиме отладки

Для подтверждения корректной работы аутентификации по ключу подключение с хост-машины было выполнено в режиме подробного вывода логов `-v`
```powershell
ssh -v -p 2222 el@127.0.0.1
```
В отладочном журнале успешно зафиксировано использование криптографического ключа `Authenticated to 127.0.0.1 (:2222) using "publickey"` после чего сессия открылась без запроса пароля

### Вывод

В ходе лабораторной работы был установлен гипервизор Oracle VirtualBox с пакетом расширений Extension Pack и развёрнута виртуальная машина (4 ГБ ОЗУ, 2 ядра ЦПУ, накопитель ~30 ГБ). На неё была установлена ОС Debian 13 (amd64, netinst) с именем хоста debian и учётной записью el. Поскольку использовался минимальный образ без графической оболочки, через консоль были вручную доустановлены и настроены окружение рабочего стола MATE и дисплейный менеджер LightDM.

Была проверена работа сети в режиме NAT (проверка соединения через ping и обновление системы командами apt update && apt upgrade), а также настроен проброс портов порт хоста 2222, порт гостя 22. На гостевой системе развёрнут и запущен сервер openssh-server, после чего успешно организован удалённый доступ с основной машины (Windows) как по паролю, так и по криптографическим ключам (ed25519).

Цель работы достигнута на практике освоены развёртывание виртуальных машин, базовая настройка Linux через терминал, управление пакетами и организация безопасного удалённого подключения по SSH.
